## 2026-08-17 | 화면-방향-고정-설정

### 요청
- 설정 화면에 화면 방향 옵션(적응형·가로·세로) 추가. 디폴트는 적응형(기존처럼 기기 회전에 따라 UI 전환), 가로/세로 선택 시 해당 방향으로 고정.

### 행동
- `OrientationHelper.kt` 신규 생성 — SharedPreferences(`rummitimer_settings`)에 `orientation` 키로 저장/로드, 상수 `ORIENTATION_ADAPTIVE`/`ORIENTATION_LANDSCAPE`/`ORIENTATION_PORTRAIT`
- `MainActivity.kt` — `orientationMode` 상태 추가, `SideEffect`에서 `requestedOrientation`을 설정값에 따라 `SCREEN_ORIENTATION_UNSPECIFIED`/`SENSOR_LANDSCAPE`/`SENSOR_PORTRAIT`로 적용
- `SettingsScreen.kt` — 화면 섹션에 화면 방향 라디오 그룹 3개 추가
- `AnalyticsHelper.kt` — `ORIENTATION_CHANGE` 이벤트 상수 추가
- 6개 로케일 `strings.xml`에 `orientation_label`, `orientation_adaptive`, `orientation_landscape`, `orientation_portrait` 추가
- `compileDebugKotlin`, `lintDebug` 실행 확인 (lint 기존 에러 3건은 본 변경과 무관함을 stash로 대조 확인)

### 결정
- 가로/세로 고정 시 `SCREEN_ORIENTATION_LANDSCAPE`/`PORTRAIT` 대신 `SENSOR_LANDSCAPE`/`SENSOR_PORTRAIT` 사용 — 방향 카테고리는 고정하되 기기를 뒤집어도(180도) 자연스럽게 반응하도록 함
- 적응형은 `SCREEN_ORIENTATION_UNSPECIFIED`로 설정 — manifest에 기존에 `screenOrientation` 속성이 없던 것과 동일한 기본 동작(시스템 자동 회전 설정 따름)을 재현
- `AndroidManifest.xml`의 `configChanges="orientation|..."`가 이미 있어 `requestedOrientation` 변경 시 Activity가 재생성되지 않고 `LocalConfiguration`만 갱신됨 — HomeScreen.kt/TwoPlayerTimerScreen.kt의 기존 `Configuration.ORIENTATION_LANDSCAPE` 분기 로직은 수정 불필요

## 2026-08-17 | 가로모드-레이아웃-잘림-수정

### 요청
- 가로 모드 옵션 적용 후 발견된 후속 버그: General Timer / Go Timer Setup / Pomodoro 등 스크롤이 없는 화면에서 가로 모드일 때 버튼이 화면 밖으로 잘리고, 배너 광고 영역과 버튼 영역이 겹쳐 버튼을 누를 수 없는 문제. 스크롤을 추가하는 대신 UI가 화면 높이/너비에 맞게 자동으로 축소되도록 요청.

### 행동
- `AutoFitContent.kt` 신규 생성 — `SubcomposeLayout`으로 콘텐츠를 제약 없이 측정해 자연 크기를 구한 뒤, 가용 영역(`constraints.maxWidth/maxHeight`)을 초과하면 `min(1f, 가용폭/자연폭, 가용높이/자연높이)` 비율로 축소해 배치하는 범용 래퍼. 절대 확대는 하지 않음(scale은 항상 1 이하), 자체 보고 크기는 축소된 콘텐츠 크기(= wrap-content처럼 동작)이므로 Column 안에서 다음 형제(예: LazyColumn)에게 남은 공간을 그대로 넘겨줌
- `GeneralTimerScreen.kt`, `PomodoroScreen.kt` — 원형 링을 `fillMaxWidth(0.72f/0.82f)+aspectRatio(1f)`(가로 기준 비율, 세로가 짧으면 넘침) 대신 고정 `size(260dp/280dp)`로 변경하고, 전체 콘텐츠 Column을 `Box(fillMaxSize, contentAlignment=Center) { AutoFitContent { Column } }`으로 감싸 화면에 맞게 축소
- `StopwatchScreen.kt` — 링+버튼 헤더 부분만 `AutoFitContent(Modifier.fillMaxWidth())`로 감싸고, 랩 기록 `LazyColumn`은 감싸지 않고 기존처럼 Column의 "남은 공간"을 받아 스크롤되도록 유지 (랩은 개수가 가변적이라 축소가 아니라 스크롤이 맞는 콘텐츠)
- `TwoPlayerSetupScreen.kt` — 콘텐츠 Column에 `Modifier.width(320.dp)` 고정 폭을 주어 내부 `Button(Modifier.fillMaxWidth())`가 무한 제약(AutoFitContent의 측정 패스) 아래에서도 정상 동작하도록 하고, `Spacer(Modifier.weight(1f))`(무한 높이 제약과 호환 불가)를 고정 `height(24.dp)`로 교체, 전체를 `Box+AutoFitContent`로 감쌈
- Pixel_8 에뮬레이터(1080x2400)를 가로로 회전해(`adb shell settings put system user_rotation 1`) General Timer(대기/실행 상태), Go Timer Setup, Pomodoro 화면을 직접 캡처해 잘림·겹침이 사라졌음을 확인. 세로 모드로 되돌려 기존과 동일하게 보이는지(회귀 없음)도 확인
- `compileDebugKotlin`, `lintDebug` 재실행 — 기존과 동일한 3건의 무관한 lint 에러만 존재, 신규 에러 없음

### 결정
- "스크롤 추가" 대신 "자동 축소"를 요청받았으므로, 화면이 좁을 때 콘텐츠를 잘라내거나 스크롤하는 대신 통째로 비율을 유지하며 줄어드는 방식을 택함 — `AutoFitContent`는 `placeable.placeRelativeWithLayer`로 배치 시점에 `graphicsLayer(scaleX/scaleY)`를 적용하므로, Compose의 히트 테스트가 레이어 변환의 역행렬을 적용해 터치 좌표를 보정해줌 → 축소된 버튼도 시각적 위치 그대로 정상 클릭됨
- `AutoFitContent`가 항상 `constraints.maxWidth/maxHeight`를 그대로 자기 크기로 보고하지 않고, "축소된 콘텐츠의 실제 크기"를 보고하도록 설계 — 그래야 StopwatchScreen처럼 헤더 다음에 오는 `LazyColumn`이 Column의 순차적 잔여 공간 배분을 통해 정상적으로 남은 공간을 받아 스크롤 가능
- 링 지름을 기존 `fillMaxWidth(fraction)` 비율값 대신 고정 dp(260/280)로 바꾼 것은 시각적 변경처럼 보이지만, 일반적인 세로 폭(360~412dp) 기준으로 원래 비율이 만들어내던 크기(약 260~300dp)와 거의 일치하도록 값을 선택해 세로 모드 외관은 그대로 유지됨
- `TwoPlayerSetupScreen`의 시작 버튼을 폭 320dp로 고정한 것은 원래 화면 전체 폭에 맞춰 늘어나던 것과 살짝 다르지만(패딩 24dp를 뺀 세로 폭과 유사한 값), `AutoFitContent`의 무제약 측정 패스와 `fillMaxWidth()`를 양립시키기 위한 필수적인 트레이드오프

### 미해결
- HomeScreen.kt, TwoPlayerTimerScreen.kt는 이미 자체적인 가로 모드 전용 레이아웃(Row 분기)을 갖고 있어 이번 수정 대상에서 제외함 — 만약 이 화면들에서도 짧은 세로 높이의 가로 기기에서 잘림이 발견되면 별도로 확인 필요
- ResultScreen.kt, TwoPlayerResultScreen.kt, ScoreInputScreen.kt은 이번 버그 리포트에 포함되지 않아 손대지 않음

## 2026-08-17 | 2인대국-설정값-드롭다운-전환

### 요청
- 2인 대국 설정 화면(장기·바둑·체스)의 "정해진 값 선택" UI(FilterChip 나열, 스크린샷 예시: "Time Limit" 1/3/5/10 min)를 Dropdown 형태로 전환. 범위를 물어본 결과 "2인 대국 설정 화면 전체"로 확정 (HomeScreen의 인원수·제한시간 선택 UI는 제외).

### 행동
- `TwoPlayerSetupScreen.kt` 하단에 `ValueDropdown` 컴포저블 신규 추가 — `ExposedDropdownMenuBox` + 읽기 전용 `OutlinedTextField`(라벨·현재 값·트레일링 화살표 아이콘) + `ExposedDropdownMenu`(`DropdownMenuItem` 목록)로 구성된 범용 Int 값 선택 드롭다운
- 장기(제한 시간), 바둑(기본시간·초읽기 시간·초읽기 횟수 3개), 체스(기본시간·증가시간 2개) 총 6개의 `Text(라벨) + Row(FilterChip...)` 블록을 각각 `ValueDropdown` 한 줄 호출로 교체 — 라벨은 `OutlinedTextField`의 floating label로 흡수되어 별도 `Text` 라벨 컴포저블 불필요
- 더 이상 쓰이지 않는 `FilterChip`, `Row`, `horizontalScroll`, `rememberScrollState` 관련 import 제거
- `MenuAnchorType`가 이번 Material3(compose-bom 2025.12.00) 버전에서 `ExposedDropdownMenuAnchorType`로 개명·deprecated 처리된 것을 컴파일 경고로 발견해 새 이름으로 교체
- Pixel_8 에뮬레이터에 설치해 장기/바둑/체스 3개 화면 모두 드롭다운 렌더링·펼침·스크롤(5개 옵션 중 2개만 보이고 나머지는 스크롤)·선택 동작을 직접 캡처로 확인

### 결정
- `ExposedDropdownMenu`는 별도 import 없이 사용 — 최신 Material3에서 `ExposedDropdownMenuBoxScope`의 멤버 함수로 제공되어 `ExposedDropdownMenuBox { ... }` 블록 안에서는 임포트 없이 바로 호출 가능 (import 시 "Unresolved reference" 컴파일 에러 발생해 확인함)
- 드롭다운 메뉴 팝업이 한 번에 2개 옵션만 보이고 나머지는 스크롤되는 것은 버그가 아니라 Material3 `DropdownMenuItem`의 기본 항목 높이 때문에 생기는 정상 동작 — 실제로 스와이프해 5개 옵션(1/3/5/10/30분) 전부 도달 가능함을 확인

## 2026-08-17 | 2인대국-타이머-원형링-UI-전환

### 행동
- `TwoPlayerTimerScreen.kt`의 `PlayerHalf` 컴포저블에 `totalSeconds: Int` 파라미터 추가 (초읽기 중이면 `byoyomiSeconds`, 아니면 `initialTimeSeconds`) — 링 진행률 계산용
- 기존 `Text("P${playerIndex+1}") + Text(시간)` 단순 텍스트 블록을, `GeneralTimerScreen`과 동일한 패턴(`Canvas`로 트랙 원 + `drawArc`로 남은 시간 비율 진행 호, 중앙에 시간 텍스트)의 190dp 링으로 교체. 링 색상은 배경색 대신 이미 상태별로 계산되어 있던 `textColor`(대기/활성/승리/패배별 대비색)를 그대로 재사용해 별도 색상 로직 추가 없이 상태(대기·활성·승리·시간초과)를 그대로 반영
- 링을 포함한 텍스트 블록 전체를 `AutoFitContent`로 감싸 좁은 절반 영역(특히 가로 모드에서 폭이 반으로 줄어드는 경우)에서도 잘림 없이 자동 축소되도록 함 — 이번 세션 앞부분에서 만든 `AutoFitContent`를 재사용
- `rotate(rotation)` 모디파이어는 그대로 `Column`에 유지해 P2의 180도 회전(상대방이 자기 쪽에서 바로 읽을 수 있도록) 동작 보존
- Pixel_8 에뮬레이터에 설치해 세로/가로 모드 모두에서 대국 시작 전(빈 링, 가득 찬 상태) / 대국 진행 중(P1 활성 링이 서서히 줄어듦, P2는 회색 대기 상태) 화면을 직접 캡처해 확인. 좌표 계산 실수로 Start 버튼 탭이 처음엔 안 먹혀서 `uiautomator dump`로 실제 clickable 영역 bounds를 확인 후 재시도해 정상 동작 검증

### 결정
- 링의 sweepAngle 계산은 `CLAUDE.md`의 "카운트다운 링은 양수 sweepAngle, 반시계 방향으로 줄어드는 효과" 규칙을 그대로 따름 (`timeSeconds/totalSeconds*360f`)
- 링 트랙/진행 호 색상을 별도로 새로 정의하지 않고 기존 `textColor`(상태별 대비색)를 그대로 사용 — Surface 배경색(bgColor)이 이미 대기/활성/승리/패배를 색으로 구분하고 있으므로, 링은 그 위에 얹히는 시각 요소로서 같은 색 체계를 따르는 것이 가장 일관적이라 판단
- 링 크기는 GeneralTimerScreen(260dp)보다 작은 190dp로 설정 — PlayerHalf 하나가 화면의 절반(세로) 또는 컨트롤 스트립을 제외한 절반(가로)만 차지하고, P 라벨·초읽기 라벨·상태 텍스트도 함께 표시해야 하므로 더 작은 고정 크기를 선택했고, 혹시 그래도 안 맞으면 AutoFitContent가 추가로 축소함

## 2026-08-17 | 바둑-초읽기-예비링-표현

### 요청
- 바둑 타이머의 초읽기(byoyomi) 중, 텍스트("Byoyomi N left")뿐 아니라 남은 횟수만큼 링을 그려서 시각적으로 표현하고, 횟수가 줄어들면 링을 하나씩 없애는 방식으로 보여달라는 요청. 스크린샷으로 현재 상태(텍스트만 있고 링은 1개) 첨부.

### 행동
- `TwoPlayerTimerScreen.kt`의 `PlayerHalf` Canvas 블록에서, `inByoyomi && !isGameOver`일 때 바깥쪽 카운트다운 링(현재 진행 중인 초읽기 회차, 트랙+진행 호) 안쪽으로 `byoyomiPeriodsLeft - 1`개의 정적인 얇은 예비 링을 동심원으로 추가 렌더링
- 예비 링은 카운트다운 없이 항상 꽉 찬 원(`drawCircle` with `Stroke`)으로 그려 "이번 회차 + 예비 N회"를 한눈에 표현. 반지름이 스트로크 두께 이하로 줄어들면(주로 5회 설정처럼 예비가 많을 때) 중앙 텍스트와 겹치지 않도록 그리기를 중단(`break`)하는 방어 로직 추가
- 기존 "Byoyomi N left" 텍스트 라벨은 그대로 유지 (정확한 숫자 정보 제공 + 시각적 링 표현을 보완)
- 장기(main=0분), 초읽기 30초, 5회로 설정해 에뮬레이터에서 실제로 대국 시작 → 30초 경과 시켜 첫 회차 소모 확인. "Byoyomi 5 left"일 때 예비 링 4개가 보이다가, 시간 초과로 "Byoyomi 4 left"로 넘어가자 예비 링이 3개로 정확히 하나 줄어드는 것을 스크린샷으로 확인

### 결정
- 예비 링 개수는 `byoyomiPeriodsLeft - 1`로 계산 (바깥쪽 카운트다운 링 자체가 "현재 진행 중인 1회"를 나타내므로 중복 카운트하지 않음)
- 예비 링 색상은 진행 중인 링과 동일한 `ringColor`를 쓰되 알파값(0.45)을 낮춰 "지금 카운트다운 중인 것"과 "대기 중인 예비"를 시각적으로 구분
- Baduk 외 Janggi/Chess는 `byoyomiPeriods`가 항상 0으로 시작해 `inByoyomi`에 진입하지 않으므로, `PlayerHalf`에 게임 종류 분기를 추가하지 않고도 자연스럽게 바둑에서만 이 표현이 나타남

## 2026-08-17 | 초읽기-예비링-간격-조정

- 방금 추가한 초읽기 예비 링들이 서로 너무 떨어져 보인다는 피드백 (스크린샷 첨부: "Byoyomi 3 left"에 링 2개가 눈에 띄게 벌어져 있음). 링이 거의 맞닿되, 구분되도록 얇은 공백만 남기는 방식으로 수정 요청.

### 행동
- `TwoPlayerTimerScreen.kt`의 예비 링 반지름 계산 방식을 "고정 배수만큼 반지름을 줄이는 방식"(`ringRadius - ringGap * i`, `ringGap = strokeWidth * 1.5f`)에서 "이전 링의 안쪽 가장자리(inner edge)를 추적해 그 바로 안쪽에 얇은 간격만 두고 다음 링을 붙이는 방식"으로 변경
- 새 로직: `edgeGap = strokeWidth * 0.12f`(고정된 얇은 간격), `innerEdge` 변수로 직전 링의 안쪽 가장자리 반지름을 누적 추적하며 `reserveRadius = innerEdge - edgeGap - reserveStroke/2f`로 다음 링 중심 반지름을 계산 → 스트로크 두께에 관계없이 항상 "edgeGap"만큼만 떨어지도록 보장
- 에뮬레이터에서 3회 설정(예비 링 2개)으로 재확인 — 링들이 서로 맞닿을 만큼 촘촘해지고 얇은 간격으로만 구분되는 것을 스크린샷으로 확인

### 결정
- 간격을 "반지름 차이"가 아니라 "가장자리 간 거리(edge-to-edge gap)"로 직접 제어하는 방식으로 바꾼 이유: 메인 링과 예비 링의 스트로크 두께가 서로 달라서(`strokeWidth` vs `reserveStroke = strokeWidth*0.6f`), 반지름 차이를 고정값으로 주면 실제 눈에 보이는 간격이 스트로크 두께에 따라 들쭉날쭉해짐. 가장자리 좌표를 직접 추적하면 항상 일정한 시각적 간격을 보장할 수 있음

## 2026-08-17 | 보드게임-타이머-직전-설정값-저장

### 요청
- 장기/바둑/체스(2인 대국) 타이머의 설정값을, 게임을 실행할 때마다 저장하고 게임이 끝나거나 앱을 다시 실행했을 때 직전 설정값이 그대로 적용되도록 요청. 기존에는 `TwoPlayerSetupScreen`의 각 값이 `rememberSaveable`로만 관리되어, 화면이 컴포지션에서 완전히 사라졌다가(메뉴 이동 후 재진입, 게임 종료 후 결과 화면 경유 등) 다시 생성될 때마다 하드코딩된 기본값(장기 10분, 바둑 30분/30초/3회, 체스 5분/3초)으로 초기화되는 문제가 있었음

### 행동
- `TwoPlayerSetupHelper.kt` 신규 생성 — `ThemeHelper`/`OrientationHelper`와 동일한 패턴으로 `rummitimer_settings` SharedPreferences에 6개 값(장기 제한시간, 바둑 기본시간·초읽기 시간·초읽기 횟수, 체스 기본시간·증가시간)의 get/set 함수 제공, 각 함수는 기존 하드코딩 기본값을 그대로 fallback으로 사용
- `TwoPlayerSetupScreen.kt` — 6개 `rememberSaveable` 상태의 초기값을 하드코딩 상수 대신 `TwoPlayerSetupHelper.getX(context)` 호출로 변경 (화면이 새로 컴포지션될 때마다 저장된 직전 값을 읽어옴)
- 시작 버튼(`onClick`)에서 `onStart(...)` 호출 직전에 해당 게임 종류의 현재 선택값을 `TwoPlayerSetupHelper.setX(context, ...)`로 저장 — "실행한 설정값"만 저장되도록, 드롭다운을 만지작거리기만 하고 시작하지 않은 값은 저장하지 않음
- 에뮬레이터에서 실제 검증: 바둑 기본시간을 기본값(30분)에서 20분으로 변경 후 시작 → 게임종료 버튼으로 종료 → 설정 화면 재진입 시 "20분"이 그대로 표시됨을 확인. 이어서 앱을 강제 종료(force-stop) 후 재실행해도 "20분"이 유지됨을 확인

### 결정
- 저장 시점을 "드롭다운 값이 바뀔 때마다"가 아니라 "시작 버튼을 눌러 게임을 실제로 실행하는 시점"으로 정함 — 사용자가 요청한 표현이 "실행한 설정값을 저장"이었고, 값을 이것저것 눌러보다가 시작하지 않고 나가는 경우까지 저장하면 사용자 의도와 다를 수 있다고 판단
- 게임 종류별로 완전히 독립된 키를 사용 (장기/바둑/체스 설정이 서로 값을 덮어쓰지 않음) — 사용자가 여러 게임을 번갈아 플레이해도 각자의 마지막 설정을 유지
